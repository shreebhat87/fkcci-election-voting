# FKCCI Election Voting Slip System — HTML Prototype

Static, clickable prototype for review before the CodeIgniter 4 + MySQL build begins.
No backend, no database — all state is mocked in the browser via `localStorage`.

## Scope (confirmed)

This is **not** a full membership-management system. It is a focused, election-day tool:

1. Master voter data (RFID Tag ID, Member ID, Name, Company, Designation, Mobile, Email)
   is imported from an Excel sheet exported from the existing (defunct) RFID system. Each
   company has exactly **2 designated members**. Photo is handled as a **separate,
   optional** step — see "Photo handling" below — not an Excel column.
2. At any of **10 simultaneous counters**, an operator scans a member's existing RFID card
   on a **Zebra RFID reader** running in **USB/Bluetooth keyboard-wedge mode** (the reader
   types the tag ID into a focused input field, followed by Enter — no SDK integration
   needed for v1).
3. The system looks up the tag against the master data:
   - **Not found** → operator sees "card not recognized", no slip printed.
   - **Found, company already voted** (i.e. the other designated member of that company
     already has an issued slip) → alert shown, **no slip printed**. This check must be
     server-side and atomic across all 10 counters to prevent a race between two counters
     scanning the two reps of the same company at the same moment.
   - **Found, eligible** → a **voting slip** is generated (Member ID, Name, Company,
     Designation, QR code, serial number, counter, timestamp) and printed via the browser
     print dialog to a standard printer.
   - Because a member's RFID can only be scanned once (the vote is now recorded), a slip
     can't be regenerated by rescanning. So every issued slip is reachable afterwards —
     from the counter's Recent Activity list, the admin voter log, and the admin
     dashboard's activity feed — via `slip.html?serial=...`, a standalone view where the
     operator/admin can view it on screen and reprint to **any** connected/network
     printer (the browser's native print dialog), not just whatever printed the first
     time. This covers printer failures, wrong tray/paper, or a counter's printer being
     down — the fix is "go to another printer," not "rescan the card."
4. The slip's QR code, when scanned (e.g. at the polling hall entrance), opens a
   verification page showing the member's photo (if on file), name, company, and slip
   validity.
5. Admin: upload/validate master data, bulk-upload member photos, dashboard of turnout
   and per-counter activity, full voter log with search/filter, CSV export, and the
   ability to **void** a wrongly-issued slip with a reason.

Explicitly **out of scope for this phase**: membership renewals, fee/payment processing,
member self-service portal, physical access control/turnstiles. The data model is kept
simple enough that these could be layered on later without rework, but nothing here
should be built for them now.

## Photo handling

Confirmed: photo is shown to the **counter operator** (to visually check the person
against the card) and on the **QR verification page** (for hall-entry staff) — it is
**never printed on the voting slip**, since counters print to thermal slip printers where
a photo would just render as a rough grayscale blob. Photo is also an **optional** field
end-to-end: a member with no photo on file is scannable, votable, and gets a slip exactly
like anyone else — the UI just falls back to an initials avatar instead of blocking
anything.

- **Bulk upload, not Excel-embedded.** Photos come in as a separate `.zip` of image files,
  uploaded independently of the Excel master-data import (see `admin-upload.html`, Step
  2). We deliberately don't try to extract images embedded inside Excel cells — that's
  fragile (position-anchored to a cell, not to data — one shifted row silently mismatches
  a photo to the wrong person) and not worth it when re-collecting individual photo files
  is straightforward.
- **Matching by filename = Member ID**, e.g. `FKCCI-001A.jpg`. No manual "map this file
  to this row" step — deterministic and doesn't get worse as the member list grows.
  Unmatched filenames (typos, stale files) are reported and skipped without affecting
  anything else; members with no matching file simply have no photo.
- **Storage**: real files under `writable/uploads/photos/{member_id}.{ext}` (not DB
  BLOBs), with the relative path saved on `members.photo_path`. Validate file type
  (jpg/png) and a sane max size/dimensions on upload; a moderate server-side resize is
  worth doing since these are just small avatar-sized displays, not print assets.
- **Never required**: nothing in the Excel import, the vote-issuing flow, or slip printing
  checks for a photo's existence. It's purely a display convenience layered on top.

## Pages

| Page | Purpose |
|---|---|
| `index.html` | Login — Counter Operator (picks assigned counter) / Election Admin |
| `counter.html` | Core scan-and-print screen used at each of the 10 counters |
| `slip.html?serial=...` | Standalone slip view/reprint — open from Recent Activity, the voter log, or the dashboard to view on screen or print to a different printer without rescanning |
| `verify.html` | QR scan result — what hall-entry staff see when they scan a printed slip |
| `admin-dashboard.html` | Turnout stats, votes per counter, companies pending, recent activity |
| `admin-upload.html` | Master data Excel import + optional bulk photo upload (matched by filename), column mapping, validation summaries |
| `admin-log.html` | Full voter log — search/filter, void a slip, CSV export |

## Viewing it

Everything is static — just open `index.html` in a browser, or serve the folder:

```
cd prototype
python3 -m http.server 8080
# open http://localhost:8080
```

On the counter screen, use the **"▶ Simulate: …"** chips to trigger the three scan
outcomes without real hardware. Demo state (who has "voted") lives in `localStorage`
under the key `fkcci_proto_state_v1` — use "↺ Reset demo data" on the admin dashboard to
start over.

## Known prototype shortcuts (will differ in the real build)

- **QR codes are decorative**, not real scannable codes (`assets/js/qr.js` draws a
  deterministic pattern with authentic-looking finder squares). The production app will
  generate real QR codes server-side in PHP (e.g. `endroid/qr-code`).
- **"Already voted" checking is done in the browser** against `localStorage`. In the real
  app this must be a single atomic MySQL transaction (e.g.
  `SELECT ... FOR UPDATE` on the company row, or a unique constraint on
  `votes(company_id)` for non-void rows) so two counters can't both issue a slip for the
  same company in a race.
- **Excel parsing/validation is simulated** with a fake progress bar and canned results.
  The real import will use a PHP spreadsheet library (e.g. `phpoffice/phpspreadsheet`),
  validate required columns and duplicate RFID tags server-side, and write to a staging
  table before committing.
- **Auth is not real** — any login succeeds. The real app needs actual operator/admin
  accounts, session handling, and probably a PIN or short session timeout per counter
  given shared kiosk usage.

## Suggested MySQL schema (starting point for the CI4 build)

```
companies      (id, name, created_at)
members        (id, company_id, member_id, name, designation, rfid_tag UNIQUE,
                 photo_path NULLABLE, mobile, email, created_at)
votes          (id, member_id, company_id, counter_no, serial_no UNIQUE, status
                 ENUM('issued','void'), void_reason, issued_at, voided_at, issued_by)
users          (id, role ENUM('admin','operator'), username, password_hash,
                 assigned_counter, created_at)
import_batches (id, filename, row_count, valid_count, error_count, imported_by, imported_at)
```

A partial unique index (or an application-level `SELECT ... FOR UPDATE` transaction) on
`votes(company_id)` where `status = 'issued'` is what actually enforces "one vote per
company" safely across 10 concurrent counters — this is the most important correctness
requirement in the whole system and needs a proper DB-level guarantee, not just an
application-level check.
